# Plan: MusicLyricsWidget — tests, P0 widget activation, P1 runtime fixes

Date: 02-10-2026 · Branch: `fix/widget-p0-p1` · Spec: the review findings P0/P1 in the session (summarised below) + `CLAUDE.md`.
Synchronised lyrics, P3 cleanup (secret storage, MainWindow debug dump) and P4 packaging are OUT of scope.

## Context

C# / .NET 8 / WinUI 3 / Windows App SDK 1.5 widget provider (Windows 11 Widgets Board). One exe:
`-RegisterProcessAsComServer` → COM server hosting `LyricsWidgetProvider`; otherwise the WinUI settings window.
Pipeline: `AudioCaptureService` (NAudio, 10 s mic) → `SongIdentificationService` (ACRCloud) → `LyricsService` (LRCLIB),
driven by `MusicRecognitionOrchestrator` (Timer, 30 s), rendered by `WidgetStateManager` into Adaptive Card templates.

Findings this plan fixes:
- P0-1 `Program.cs` class factory returns `Marshal.GetIUnknownForObject(...)` (classic COM CCW). Microsoft's reference uses
  `MarshalInspectable<IWidgetProvider>.FromManaged(...)`. Widget Host cannot use the current object.
- P0-2 Manifest `<Definition>` lacks `<Screenshots>` (Required per "Widget provider package manifest XML format").
- P0-3 `AllowMultiple` defaults to true; provider supports one widget id.
- P1-4 `AudioCaptureService` creates a new `WaveInEvent` per capture and never disposes the previous one (device handle leak).
- P1-5 ACRCloud error codes (≠0, ≠1001) and HTTP errors are reported as "no music".
- P1-6 Orchestrator Timer uses `async _ => await RecognizeOnceAsync(_cts.Token)` (async void; reads field after Stop → crash). No overlap guard.
- P1-7 A single unrecognised sample shows "Ready — tap Listen Now" while the loop runs; lyrics vanish. Also every 30 s cycle
  replaces the lyrics view with "Listening…"/"Identifying…" (flicker).
- P1-8 COM server process never exits; runs on STA (Microsoft sample: MTA).
- P1-9 `LyricsService` swallows every exception (`catch { return null; }`) and takes the first `/api/search` hit blindly.
- P1-10 Errors render twice (first "Unknown error"); provider state is touched from several threads without synchronisation.

## Task 4: Orchestrator robustness

Goal: no crash on Stop, no overlapping cycles, no flicker, honest states.

Behaviour (spec):
- Timer callback must not be an async lambda: capture `var token = _cts.Token` locally in `Start`, timer callback
  `_ => _ = RecognizeOnceAsync(token)`. `RecognizeOnceAsync` never lets an exception escape (OperationCanceledException is
  silent; anything else → Error state).
- Overlap guard: if a cycle is already running, `RecognizeOnceAsync` returns immediately (Interlocked flag, reset in `finally`).
- `Stop()`: dispose the timer, cancel the CTS, drop references (do not dispose the CTS — in-flight cycles still hold its token),
  reset song/lyrics/miss counter, set `Idle`. After cancellation an in-flight cycle must not emit any further state.
- New `RecognitionState.NoMatch` (add after `Listening`… order irrelevant; append at the end of the enum).
- "Showing a song" = `State == DisplayingLyrics && CurrentSong != null`. While showing a song, a cycle emits NO
  Listening/Identifying states (runs silently).
- Result handling:
  - match, same song as `CurrentSong` (SongInfo equality) → no lyrics refetch (even if lyrics were null); ensure state is
    `DisplayingLyrics` (set it only if not already); reset miss counter.
  - match, different song → `CurrentSong = song`, `CurrentLyrics = null`, `FetchingLyrics`, fetch, `CurrentLyrics = result`,
    `DisplayingLyrics`, raise `SongRecognized` only when lyrics non-null; reset miss counter.
  - no match → increment miss counter; if a song is current and misses < `MissesBeforeClearingLyrics` (const 2) → keep/restore
    `DisplayingLyrics`; otherwise clear song+lyrics and set `NoMatch`.
  - exception → `ErrorMessage = ex.Message`, `Error`, raise `ErrorOccurred` once. Keep `CurrentSong` so a later cycle with
    the same song restores `DisplayingLyrics`.
  - Amendment (controller rulings after review): `OperationCanceledException` is silent only when the cycle's own token is
    cancelled; any other OCE (e.g. HttpClient timeout) takes the error path. The same-song no-refetch shortcut applies only
    when the lyrics lookup for that song completed; a lookup that threw is retried on the next same-song match.
- `WidgetStateManager`: map `NoMatch` → listening template, statusText `No music recognised yet — listening again shortly...`.

Tests: `MusicRecognitionOrchestratorTests` with fakes for the three interfaces (fakes return queued results; capture can be
blocked on a `TaskCompletionSource` for the overlap test). Record `StateChanged` sequence.
- first match → `[Listening, Identifying, FetchingLyrics, DisplayingLyrics]`, `CurrentLyrics` set, `SongRecognized` once;
- second cycle same song → no states emitted, lyrics fetched once in total;
- one miss while showing → still `DisplayingLyrics`, lyrics kept; second consecutive miss → `NoMatch`, `CurrentSong` null;
- miss with nothing shown → ends in `NoMatch` (never `Idle`);
- identifier throws → ends in `Error`, `ErrorMessage` == exception message, `ErrorOccurred` raised exactly once;
- overlap: second `RecognizeOnceAsync` while the first is blocked returns at once; capture called once;
- cancellation after capture → no `Identifying`/later states emitted after cancel.
Plus a `WidgetStateManagerTests` case for `NoMatch` (template + statusText + placeholder invariant).

Commit: `Gør genkendelses-loopet robust: ingen overlap, ingen flimmer, NoMatch-tilstand`.
